一、今日要闻

要闻目录：① WorkBuddy 补齐问答切换、任务归属与历史恢复；② OpenCode 披露 Browse 重写，事件驱动 Agent 仍处内部试用。

1. WorkBuddy 发布 5.11.3：问答与执行切换更直接，补上任务可靠性缺口

事件：腾讯官方日志将 5.11.3 标为 2026 年 11 月 15 日发布，新增会话流快速问答入口，可发起推荐问答或切回 Agent 模式。同时修复云端定时任务混入“这台电脑”列表、本地历史会话偶发丢失，以及特定 CE 会话缺少项目资源注册、导致相关 MCP 工具和技能目录不可用等问题。日志没有给出分钟级首发时间，也没有注明本版本的分地区、分套餐推送进度。来源

为什么重要：用户需要判断是否执行、辨认运行位置并恢复上下文。任务归属或历史记录出错，会把原本可完成的工作变成重复提交和人工排查。我的判断是，这类修复影响持续使用的可信度，采购和留存评估应把它与模型能力分开计量。

接下来观察：用同一组云端与本地定时任务，核对列表归属、历史恢复和工具可用性是否稳定；官方所列修复尚不能替代真实环境中的回归结果。本期没有价格调整或全面扩大开放范围的证据。

2. OpenCode 披露 Browse 的 Rust 重写，Slack／GitHub 事件接入仍是内测

事件：11 月 15 日 03:51（北京时间），@thdxr 发帖称已用 Rust 重写 OpenCode Browse，并重做所需的 Playwright／Patchright 部分，称花费“60 美元”。这是开发者的工程自述，未说明成本口径，也未提供可直接比较的维护工时、兼容性或成功率数据。05:48，同一账号称团队正在试用尚未发布的控制台能力，让 Agent 接收 Slack、GitHub 等事件，部分成员已让自己的 Agent 回复 Slack 消息。重写原帖；内测原帖

为什么重要：事件接入改变了工作的起点：任务可以由外部系统变化触发，执行者也不必与本人同时在线。对团队产品而言，竞争因此延伸到谁能识别事件、承接上下文并以合适身份行动。重写成本低是供给侧信号；更大的产品机会是把这种能力变成可追踪、可停止的工作流程。

接下来观察：等待正式发布说明明确开放对象、事件类型、回复权限及失败重试方式。11 月 16 日 01:07:59（北京时间），@thdxr 继续评论这类交流是否值得人类参与；这条凌晨增量是对原内测的讨论，没有新增公开可用范围。凌晨原帖

四、趋势分析

1. Agent 的产品单位正在从一次对话延伸到持续任务。 当日 OpenCode 的事件内测让外部消息成为任务起点，WorkBuddy 对任务归属和历史记录的修复则暴露了任务延续所需的底层状态。我的推论是，应用差异会越来越体现为事件、任务、执行环境和交付物能否连起来：用户离开后还能追到结果，才有条件把工作长期交给它。可验证信号是公开产品能否展示一次事件触发到最终产物的完整记录，而非只展示即时演示。内测；日志

2. 生成工具变便宜，运营可靠性仍要逐项付成本。 同日“60 美元重写”的自述和 WorkBuddy 的历史、目录、任务列表修复，共同提示了开发与持续交付之间的距离。前者可能降低尝试新实现的门槛，后者说明产品还需要管理长期状态与复杂环境。对产品预算，我更看重每个验收合格任务消耗的推理、复核和维护总量。近期 Steve Yegge 的会议材料也描述了 Agent 产出超过用户吸收能力的问题，属于个人运营经验。信号应是重写后的兼容回归、故障率和维护负担，而非一次生成账单。任务修复；重写；会议材料，11 月 11 日

3. 持久在线的收益，要靠明确的身份与执行边界兑现。 OpenCode 当日描述的“随时与同事的 Agent 交流”，叠加 WorkBuddy 对云端、本地任务归属的修复，说明界面必须让人看清谁在何处做了什么。近期 OpenAI 部署文章提供了独立 Agent 身份与凭据隔离的做法；Cursor 11 月 13 日事故复盘则称，历史 Agent 轨迹中的未脱敏凭据参与了后续入侵链。我的判断是，企业产品不能把“接通更多工具”直接计为可交付能力，权限撤回和行动追溯会影响实际部署范围。观察信号是管理员能否按 Agent 撤销访问、追溯事件，并停止相关任务。当日内测；任务边界；部署实践；Cursor 原始复盘
